# DocProof 技术路线与架构设计文档

## 一、项目概述

**DocProof** 是一款基于 **LLM + OCR** 的本地文档校对工具，面向公文、年鉴、地方志等中文长文档场景。系统以 **"本地 HTTP 服务 + 浏览器客户端"** 为核心架构，在 Windows 主机上运行一个轻量 HTTP 服务，用户通过任意现代浏览器访问即可完成文档上传、AI 纠错、人工复核与导出全流程。

**核心定位**：单机/小团队内部使用的私有化校对工具，数据不出本机，敏感凭据加密存储。

## 二、技术路线

### 2.1 整体路线选择

| 维度 | 选型 | 理由 |
|------|------|------|
| 服务端语言 | **Python 3.10+** | 生态成熟，HTTP/加密/文件处理库丰富 |
| HTTP 框架 | **Python 标准库 `http.server`** (`ThreadingHTTPServer`) | 零第三方依赖，PyInstaller 打包体积最小 |
| 客户端 | **原生 HTML + CSS + JavaScript**（单页应用） | 无需 Node.js 构建链，浏览器直接渲染 |
| LLM 接入 | **DeepSeek V4 系列**（OpenAI 兼容接口） | 中文校对效果好，支持 flash / pro 两档 |
| OCR | **讯飞开放平台 API** | 中文 OCR 准确率高，支持图片与扫描版 PDF |
| 文档解析 | **PyMuPDF + python-docx** | PDF 文本提取 / DOCX 结构保留 |
| 敏感数据加密 | **Windows DPAPI**（`CryptProtectData`） | 绑定当前 Windows 用户，换机器不可解密 |
| 密码存储 | **PBKDF2-HMAC-SHA256**（20 万次迭代 + 16 字节随机盐） | 行业标准抗暴力破解 |
| 打包部署 | **PyInstaller --onefile** | 单 EXE 分发，运行无需 Python 环境 |

### 2.2 技术选型决策说明

**为何不选 Flask/FastAPI？**

> 项目核心约束是 **PyInstaller 单文件打包体积**。引入 Flask（~15MB）或 FastAPI（~20MB+ uvicorn）会导致 exe 从 ~20MB 膨胀到 60MB+。标准库 `http.server` 虽然手写路由繁琐，但在本项目路由数量有限（~15 个）的前提下性价比更高。

**为何不选 React/Vue 前端框架？**

> 客户端定位是 **"工具型单页应用"**，交互不复杂（上传 → 预览 → 纠错 → 采纳 → 导出）。原生 JS + DOM 操作足以胜任，避免了前端构建链（Node.js / npm / Vite）的引入，降低部署门槛。

**为何同时支持 flash 与 pro 两个模型？**

> 根据实测数据：
> - **flash**（非思考模式）：事实类错误检出率高、速度快、成本低（每万字约 ¥0.054）
> - **pro**（思考模式）：细粒度语法/标点问题检出能力强，但误报率显著高于 flash（12 条 vs 3 条），成本是 flash 的 4.5 倍
>
> 默认推荐 flash，用户可按需切换 pro。

### 3.2 模块职责划分

| 模块 | 文件 | 核心职责 |
|------|------|----------|
| **HTTP 层** | `main_server.py` | 路由分发、鉴权中间件、会话生命周期管理、NDJSON 流式响应 |
| **用户体系** | `users.py` | 用户名密码登录、Token 生成/校验、PBKDF2 哈希、限流计数、用户 CRUD |
| **配置管理** | `config.py` | 全局配置加载/保存、DPAPI 加解密、规则预设、原子写保障 |
| **文档解析** | `core/docload.py` | docx/txt 直接提取文本；PDF 文本版提取；扫描版/图片标记需 OCR |
| **OCR** | `core/ocr_xfyun.py` | 讯飞 OCR 调用，支持图片（JPG/PNG）和扫描版 PDF |
| **LLM 客户端** | `core/deepseek.py` | OpenAI 兼容接口封装，支持 flash/pro 模型流式调用 |
| **校对引擎** | `core/proofread.py` | 分页分块、跨页上下文拼接、错误定位（多级模糊匹配）、规则过滤、二次复核 |
| **导出** | `core/exporter.py` | txt→txt 直替换；docx→docx 保留格式改写；PDF/图片→docx 生成 |
| **数据模型** | `core/models.py` | Page / ErrorItem / TokenUsage 等纯数据类定义 |

### 3.3 数据流（核心纠错流程）

```
用户上传文件
    │
    ▼
[1] docload.py: 解析文档 → 分页提取文本
    │  (docx: python-docx 提取段落+表格)
    │  (txt: 按行/分页)
    │  (pdf: PyMuPDF 提取文本层；若无文本层则标记需 OCR)
    │
    ▼
[2] 注册会话：SESSIONS[session_id] = {user, pages, doc_ctx, ...}
    │
    ▼
[3] proofread.py: 分页分块 + 跨页上下文拼接
    │  每页 ~N 字符分块，每块附带：
    │  · context_prev: 上一页末尾 200 字
    │  · context_next: 下一页开头 200 字
    │
    ▼
[4] deepseek.py: 构造 Prompt + 流式调用 LLM
    │  系统提示词：校对专家，检查错别字/语病/标点/数据矛盾
    │  规则注入：用户启用的预置规则 + 自定义规则
    │  返回 JSON 格式错误列表
    │
    ▼
[5] proofread.py: 错误定位（多级策略）
    │  ① 精确匹配原文 offset
    │  ② 标点归一化后匹配
    │  ③ 长前缀匹配 + 空格归一化
    │  ④ 数字归一化（中文↔阿拉伯数字）
    │  ⑤ 最长公共子序列回退
    │
    ▼
[6] 二次复核（可开关）
    │  对每条错误再调用一次 LLM，判断：
    │  · confirmed（明确错误）
    │  · uncertain（存疑）
    │  · rejected（误报）
    │
    ▼
[7] NDJSON 流式推送至浏览器
    │  {"type":"progress", "chunk":1, "total":5, "usage":...}
    │  {"type":"review", "chunk":1, "confirmed":3, "uncertain":1}
    │  {"type":"done", "errors":[...], "total_usage":...}
    │
    ▼
[8] 浏览器渲染错误列表 → 用户逐条采纳/忽略
    │
    ▼
[9] exporter.py: 按 corrections 原位改写 → 下载修正后文件
```

### 4.2 校对规则体系

```
预置规则开关（默认全关闭）：
├── check_cn_number_space     # 数字与汉字间加空格
├── check_en_number_space     # 英文与汉字间加空格
├── check_full_half_punct     # 全角/半角标点统一
├── check_redundant_space     # 清除句中多余空格
└── check_number_format       # 数字格式（千分位/单位）

自定义规则（用户自由输入文本）：
"检查日期格式是否统一为 YYYY 年 MM 月 DD 日"
"检查人名前后是否有错误空格"
"检查计量单位是否规范（如 '公里' vs '千米'）"
...
```

规则注入方式：在构造 LLM Prompt 时，将启用的开关和自定义规则合并为指令段，引导模型按特定维度检查。

### 4.3 二次复核机制

```
主纠错 Pass:
  LLM 对每个文本块输出错误列表
      │
      ▼
二次复核 Pass（可开关）:
  LLM 对每条错误单独调用，判断置信度
      │
      ├── confirmed（明确错误）→ 标记为高优先级
      ├── uncertain（存疑）   → 标灰，需人工判断
      └── rejected（误报）    → 从错误列表移除
      │
      ▼
前端展示：
  明确错误 → 红色高亮，默认选中
  存疑错误 → 灰色高亮，默认未选
```

## 五、安全架构

### 5.1 加密策略分层

| 数据类型 | 加密方式 | 存储位置 | 可恢复性 |
|---------|---------|---------|---------|
| LLM API Key | **DPAPI 加密** | `_server_config.json` / `_users.json` | 仅当前 Windows 用户可解密 |
| 讯飞 OCR 凭据 | **DPAPI 加密** | 同上 | 仅当前 Windows 用户可解密 |
| 用户密码 | **PBKDF2-SHA256**（20 万次迭代） | `_users.json` | 不可逆 |
| Session Token | 明文（随机生成） | `_sessions.json` | 7 天有效期，可吊销 |
| 非敏感配置 | 明文 | `_server_config.json` | 可读但不含密钥 |

### 5.2 防攻击措施

| 威胁向量 | 防护手段 |
|---------|---------|
| **Token 暴力破解** | `secrets.compare_digest` 常时比较，PBKDF2 慢哈希 |
| **会话劫持** | Token 绑定 username，跨用户会话返回 404 |
| **SSRF 攻击** | `llm_base_url` 校验内网/回环地址（已配 Key 时拒绝） |
| **并发滥用** | 单用户 2 并发纠错 + 120 次/分钟 API 限流 |
| **配置文件篡改** | 原子写（临时文件 + `os.replace`），防止并发损坏 |
| **密钥泄露** | 浏览器不返回密钥原文，DPAPI 密文绑定 Windows 用户 |
| **客户端断连** | 哨兵异常 `_ClientDisconnected` + `_SilentHTTPServer` 静默处理 |

### 5.3 SSRF 防护逻辑

```
validate_llm_base_url(url):
    ① 协议检查：仅允许 http:// 或 https://
    ② Host 解析：
       - 公网域名 → 放行
       - 内网/回环/链路本地/多播/保留地址 → 检查第 ③ 步
    ③ 特殊放行：仅当全局未配置 LLM API Key 时，允许指向本机
       （开发调试场景，无密钥可泄露）
    ④ 已配 Key 时 → 一律拒绝内网地址
```

## 八、扩展性设计

### 8.1 LLM 服务商扩展

服务商以 **"预设"** 方式配置，新增服务商需在 `config.py` 的 `PROVIDER_PRESETS` 列表中添加条目：

```python
{
    "name": "新服务商",
    "value": "provider_key",
    "base_url": "https://api.example.com/v1",
    "models": ["model-a", "model-b"],
    "default_model": "model-a"
}
```

底层客户端为 OpenAI 兼容接口，任何符合该协议的服务商均可使用。

### 8.2 校对规则扩展

- **预置规则**：在 `config.py` 的 `PRESET_SWITCHES` 字典中添加新的开关项
- **自定义规则**：用户可在前端自由输入，无需代码变更
- **规则注入**：所有规则在 LLM Prompt 构造时动态拼装

### 8.3 多节点扩展（未来方向）

当前为单机架构，未来若需多节点部署可考虑：

- 将 `SESSIONS`、`_users.json`、`_sessions.json` 迁移到 Redis / PostgreSQL
- HTTP 层前增加 Nginx 反向代理与负载均衡
- DPAPI 替换为云 KMS / HSM

## 十、技术债务与优化方向

| 类别 | 现状 | 优化方向 |
|------|------|---------|
| **HTTP 框架** | 标准库手写路由 | 若路由数增长，考虑迁移到 Litestar/Starlette（仍轻量） |
| **前端** | 原生 JS 单文件 | 可考虑迁移到 Alpine.js / htmx 增强交互 |
| **并发模型** | `ThreadingHTTPServer`（每请求一线程） | 高并发场景可切换 `asyncio` + aiohttp |
| **日志** | 文件轮转（2MB × 5） | 可接入结构化日志 + 集中采集 |
| **会话存储** | 文件 I/O | 多节点场景需迁移到 Redis |
| **OCR** | 仅讯飞一家 | 可接入本地 PaddleOCR 降低外部依赖 |
| **LLM** | 仅 DeepSeek V4 | 已预留扩展点，可按需增加 Gemini / Claude 等 |
